# Release

Automates the release process of `CONTRIBUTING.md`. Everything the user reads is in French (see `CLAUDE.md`), except the release notes themselves, which are written in English for the players.

Repo `KerdanetYvan/age-of-alloys` (public). Version lives in `mod_version` of `gradle.properties`. The build produces `build/libs/ageofalloys-<version>.jar`. The changelog is `CHANGELOG.md` (French, Keep a Changelog format, sections `## [Non publié]` and `## [X.Y.Z] - AAAA-MM-JJ`). The banner of a version is generated by `.claude/skills/release/ReleaseBanner.java` (JDK 17, no dependency, run from the repository root).

## Usage

`/release <X.Y.Z>`. With `--dry-run`, or without a version, **only preview** (see "Preview"): nothing is written in the project, nothing is tagged, nothing is published.

## Why two phases

`main` is protected and one ticket = one branch = one PR, so the release commit cannot go to `main` directly: it goes through the branch of the release ticket and a PR that **the user merges**. The tag and the GitHub Release must point at the commit that the squash merge created on `main`, so they are made **after** the merge.

## Phase A: prepare (on the release ticket's branch)

1. **Preconditions**, stop with the detail if one fails:
   - the version is SemVer (`X.Y.Z`) and greater than the current `mod_version`;
   - the current branch is not `main` and is the branch of a release ticket (`chore/<n>-...`, started with `start-ticket`);
   - the working tree is clean (`git status --short`);
   - the tag `vX.Y.Z` does not exist (`git tag -l vX.Y.Z`, `git ls-remote --tags origin vX.Y.Z`).
2. **Changelog check**: the `[Non publié]` section is not empty, otherwise stop.
3. **Edit**:
   - `CHANGELOG.md`: `## [Non publié]` becomes `## [X.Y.Z] - <today, from date +%F>`, and a new empty `## [Non publié]` section is recreated above it;
   - `gradle.properties`: `mod_version=X.Y.Z`;
   - the banner: first `java .claude/skills/release/ReleaseBanner.java --check`, which must exit 0 (it redraws the original title and proves that the drawing rules still match), then `java .claude/skills/release/ReleaseBanner.java X.Y.Z docs/assets/releases/banner-vX.Y.Z.png`. It shows "AoA vX.Y.Z" on the banner without text. Never draw the banner by hand.
4. **Check**: `./gradlew build` must succeed, then the version check of `open-pr` ("Version number matches the release being prepared").
5. **Commit** with the `commit` skill: `chore(release): vX.Y.Z`, staging by name `CHANGELOG.md`, `gradle.properties` and `docs/assets/releases/banner-vX.Y.Z.png`. Open the PR with `open-pr` **only when the user asks**.

## Phase B: publish (only after the user says the PR is merged)

6. `git switch main && git pull`. Check that `mod_version` is `X.Y.Z`, that `CHANGELOG.md` has the `[X.Y.Z]` section and that `docs/assets/releases/banner-vX.Y.Z.png` exists, then run `./gradlew build`. The jar `build/libs/ageofalloys-X.Y.Z.jar` must exist.
7. **Write the release notes** in a file of the session scratchpad (never in the repo), in English, with this template:

   ```markdown
   ![Age of Alloys vX.Y.Z](https://raw.githubusercontent.com/KerdanetYvan/age-of-alloys/vX.Y.Z/docs/assets/releases/banner-vX.Y.Z.png)

   > **The best of every metal.** <one or two sentences saying what the mod is>

   ## What's new
   <the new features, grouped by theme (alloys, tools, compatibility), worded for players>

   ## Known limits
   <what this version does not do yet, without mentioning tickets>
   ```

   - Sources: the new features come from the `[X.Y.Z]` section of `CHANGELOG.md` (French, rewritten in English); the pitch from the slogan of `docs/identity.md` and the concept of the README; the limits from `ROADMAP.md` (the "Reporté" section and the steps that are not done).
   - The banner URL points at the **tag** of the version, not at `main`, so the image never changes. The tag is pushed before the release is created, so the URL exists by then.
   - Style: write for players. No ticket or PR number. No technical jargon (datagen, providers, tags) unless it matters to a player. Promise nothing that is postponed. Invent nothing that is not in the changelog.
8. **Ask for explicit confirmation**. The recap shows, in French: version, commit that will be tagged (`git rev-parse --short HEAD`), jar, whether it is flagged as a pre-release, the banner (display the image file with the Read tool) and the **full notes** (in a quote block, in English). Take the user's corrections into account and show the notes again if they change. A tag and a release are public and hard to undo. Do nothing before the answer.
9. After the confirmation:
   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   gh release create vX.Y.Z build/libs/ageofalloys-X.Y.Z.jar --title "vX.Y.Z" --notes-file <notes> [--prerelease]
   ```
   Use `--prerelease` while the major version is `0` (beta).
10. Give the release link as a markdown link, then remind the user that CurseForge and Modrinth are separate (ticket #70) and not handled here.

## Preview (`--dry-run` or no version)

Report, in French, without writing anything **in the project**:
- the current version and the target version, and which preconditions of step 1 hold or fail (a failing branch or clean-tree check is information here, not an error);
- the source of the notes: the `[X.Y.Z]` section if it already exists in the changelog (version already prepared or published), otherwise `[Non publié]`, or that it is empty;
- the banner: generate it with `ReleaseBanner.java` into the session scratchpad (outside the project), then display it with the Read tool;
- the notes, written as in step 7 and displayed in the conversation, not in a file;
- the jar name, the tag, and whether `--prerelease` would be used;
- the proof that the project was not touched: `git status --short` (nothing new) and `git tag -l`.

## Rules

- Never commit or push to `main`.
- Never create or push a tag, and never publish a release, without the confirmation of step 8, asked right before.
- Never merge a PR; the user merges ("Squash and merge").
- Release notes are written in English for the players, while the changelog stays in French. No ticket or PR number in the notes.
- The banner is always generated by `ReleaseBanner.java`, never drawn by hand.
- No attribution line in the commit or in the release notes (explicit decision of the repo owner).
- If a check fails, stop and report; do not fix it silently and do not skip it.
- `--dry-run` writes nothing in the project: no file, no commit, no tag, no release.
